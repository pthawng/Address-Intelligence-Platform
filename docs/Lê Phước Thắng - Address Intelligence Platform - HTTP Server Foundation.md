# HTTP Server Foundation

## Architecture

`internal/platform/httpserver` provides server.go, router.go, middleware.go,
request.go, response.go and error.go. The former httpapi mapper has moved here;
there is one error contract and no duplicate mapper. No dependencies were added.
Domain/application continue to use apperror and cannot import httpserver.

Bootstrap opens the listener, injects a logger and request base context into
httpserver.New, then calls Server.Serve. It owns the existing shutdown sequence:
stop accepting connections, drain with the shared SHUTDOWN_TIMEOUT deadline,
cancel request contexts and force-close on deadline, then close dependencies.
Startup/serving errors propagate; expected http.ErrServerClosed is normalized.
The server constructor never uses DefaultServeMux or default ListenAndServe.

## Server limits

| Environment | Default | Server field |
| --- | --- | --- |
| HTTP_READ_HEADER_TIMEOUT | 5s | ReadHeaderTimeout |
| HTTP_READ_TIMEOUT | 10s | ReadTimeout |
| HTTP_WRITE_TIMEOUT | 15s | WriteTimeout |
| HTTP_IDLE_TIMEOUT | 60s | IdleTimeout |
| HTTP_MAX_HEADER_BYTES | 32768 (32 KiB) | MaxHeaderBytes |

Config loading and the server constructor reject zero/negative limits. Invalid
integer syntax/overflow fails startup. HTTP settings apply only to the API.
Docker receives these through its existing env_file; examples include the limit.
These are JSON API defaults, to be tuned against measured workloads.

ReadTimeout covers headers and body, while ReadHeaderTimeout covers headers.
WriteTimeout is a socket write deadline, not an application execution deadline;
provider/database calls must use request contexts and explicit operation budgets.
MaxHeaderBytes does not limit bodies; net/http also applies its own parsing buffer
allowance. Request-line/header parser errors (including 431) happen before the
router and retain net/http's protocol response format.

TLS is expected at the deployment ingress/reverse proxy for the current Serve
setup. Forwarded headers are not trusted or used to rewrite client identity.
CORS, authentication and rate limiting require explicit product/deployment policy
and are not implicitly enabled. Streaming/upload routes need their own reviewed
limits; these defaults target the project's small JSON API requests.

## Routes and JSON

```go
router := httpserver.NewRouter()
router.Handle("POST /addresses/resolve", func(w http.ResponseWriter, r *http.Request) error {
    var input ResolveRequest
    if err := httpserver.DecodeJSON(w, r, &input, httpserver.DefaultMaxBodyBytes); err != nil {
        return err
    }
    result, err := service.Resolve(r.Context(), input)
    if err != nil {
        return err
    }
    return httpserver.JSON(w, r, http.StatusOK, result)
})
```

Register routes before serving. Go ServeMux method/path patterns, PathValue,
GET-to-HEAD behavior and canonical redirects are preserved. Router-generated
404/405 use the error envelope; Allow is computed by ServeMux, including methods
from overlapping patterns. Route handlers use the shared error adapter. HandleHTTP
is available for existing http.Handler implementations; they own their responses.

DecodeJSON enforces application/json (parameters allowed), a positive explicit
byte limit and one non-null JSON value. It rejects malformed input, unknown struct
fields and trailing values/data. The default helper limit is 1 MiB. Actual reads
are bounded for chunked requests too; handlers must call the helper to apply this
limit. JSON validation is separate from domain validation; duplicate keys and
case-insensitive field matching retain encoding/json semantics.

| Transport error | HTTP |
| --- | --- |
| INVALID_REQUEST | 400 |
| REQUEST_TOO_LARGE | 413 |
| UNSUPPORTED_MEDIA_TYPE | 415 |

JSON marshals before sending headers so encoding failures reach the 500 mapper.
It suppresses the body for HEAD and rejects statuses that forbid JSON bodies.
For 204, return httpserver.NoContent(w, r). A network write failure aborts; it does
not attempt to append a second error. Return handler errors before committing
headers/body. Error responses preserve the Error Foundation envelope/request ID.

## Middleware

Order: request ID and access logging -> panic recovery -> router/handler.
Request IDs are generated by the existing logging foundation. Uncommitted panics
produce generic JSON 500; panic values are never returned or logged. Stale response
headers are cleared, retaining the server request ID. Panics after write/flush or
hijack abort with http.ErrAbortHandler; partial responses are never replaced.
Explicit http.ErrAbortHandler is preserved. Recovery applies to the handler
goroutine only. Use http.ResponseController for flush, hijack and deadlines.
Hijacked connections require their own lifecycle if introduced in future features.

## Verification

Tests cover constructor limits, config defaults/overrides/runtime scope, a real
server rejecting oversized headers, routing 404/405/Allow/path parameters/HEAD,
JSON validation and chunked limits, safe panic recovery, and response encoding
failures. Existing bootstrap tests exercise graceful drain, forced shutdown,
request cancellation, listener failure and health behavior through the new server.
